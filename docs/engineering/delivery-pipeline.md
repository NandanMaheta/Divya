# Delivery pipeline v2

The **canonical operating model** for building every Swastik feature, current and future. When another document describes the flow differently, this one wins. Owner-approved on 2026-11-14.

**Goal:** maximum speed and minimum token usage, with **no compromise** on code quality, practices, tests, flow or outcomes.

**Principle:** quality comes from deterministic gates (tests written first by a separate agent, CI, business-rule traceability, golden scenarios, mutation tests, fresh-context review, owner gates). Those never change. What we remove is work that feeds no gate: re-reading context, repeated hand-offs, self-validation scaffolding, environment fixing, verbose output.

---

## 1. Risk tiers

Every feature in `docs/product/modules.md` has a **Tier**:

|             | **Tier A**: money, ledger, deals, auth, PII, migrations of those                      | **Tier B**: everything else (CRUD, screens, reports, settings, engagement, data import)               |
| ----------- | ------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------- |
| Research    | Yes (`researcher`)                                                                    | Only if the feature uses new external tech or APIs                                                    |
| Spec + plan | Separate steps: `spec-writer` (Opus) → owner approves → `architect` (Opus)            | **One step**: `architect` writes `spec.md` + `plan.md` + `brief.md` together; the owner approves once |
| Tests       | Separate `test-engineer` (Sonnet, high effort), written first                         | Separate `test-engineer` (Sonnet, medium effort), written first                                       |
| Code        | `backend-dev` / `admin-dev` / `mobile-dev` / `data-dev` (Sonnet, high)                | Same agents (Sonnet, medium)                                                                          |
| Review      | `reviewer` + `security-reviewer` (Opus)                                               | `reviewer` (Opus); `security-reviewer` only if the feature touches endpoints, auth, PII or files      |
| Extra gates | 100% branch coverage + mutation score ≥ 85% on money/auth code; owner approves the PR | Normal coverage targets; PR may auto-merge when green                                                 |

Both tiers keep: tests written **first, by a different agent from the coder**; all CI checks; BR traceability; golden scenarios; independent review; owner gates on the spec and on production.

## 2. Lean context (tokens)

1. **Feature brief** `specs/NNN-*/brief.md` (template: `.specify/templates/feature-brief-template.md`), ≤ 1 page: goal, rule IDs, acceptance criteria (IDs only + one line each), public API surface, files to touch, risks. **Every build/review agent reads the brief first** and opens `spec.md` / `plan.md` / contracts only for the section it needs.
2. **Code map** `docs/engineering/codemap.md` (generated by `scripts/gen-codemap.sh`): exported symbols per Go package and TS package. Agents read it instead of grepping the codebase to learn what exists. Regenerated by the conductor after each merge.
3. **Length caps:** spec ≤ 150 lines, plan ≤ 200 lines (details go in `contracts/` and `data-model.md`), research ≤ 120 lines, agent reports ≤ 10 lines, conductor replies short (status tables only when the owner asks or once a day).
4. **Fresh conductor session per milestone** (e.g. per feature merged, or when a chat grows long). Continuity lives in the repo: `docs/engineering/handover.md` (decisions, status, next steps). A new session reads CLAUDE.md + handover.md and continues.
5. **No repetition in prompts:** conductor prompts reference files and skills instead of restating their content.

## 3. Fewer hand-offs, same separation (tokens + time)

1. **Slices, not micro-tasks:** 8–20 slices per feature. A slice = one coherent unit (e.g. "outbox relay"), ≤ ~400 changed lines, its own tests, one done command, one commit pair (`test(...)` then `feat(...)`).
2. **First slice is always a compile skeleton:** exported types and function signatures returning `errNotImplemented`, so every test file compiles from day one and each slice's done command can go red/green independently.
3. **Batched passes:** one `test-engineer` run writes the tests for all ready slices (or one large phase); then one developer run implements them. A feature normally needs 1–2 test passes and 1–2 code passes, not one per phase.
4. **Test-first stays strict:** test files from the test pass are listed as `protected_tests`; the hook blocks implementers from editing them; the reviewer checks `git log` order (test commit before implementation).

## 4. Fast machinery (time)

1. **Shared Postgres per test package:** `dbtest.New(t)` starts one PostgreSQL 18 container per package, migrates a template database once, and gives each test its own fresh database cloned from the template (`CREATE DATABASE … TEMPLATE …`). Same isolation, seconds instead of minutes.
2. **Ready environment at session start:** the SessionStart hook runs `scripts/dev-env.sh` (starts Docker if available, checks tool versions). Linting always uses the pinned version via `make lint-go` (`go run …golangci-lint@v2.15.0`), never whatever binary is on PATH.
3. **Targeted runs while working:** the slice's done command and `-run` filters only; the full affected suite once per pass; the full repository suite in CI.
4. **No self-validation scaffolding:** test writers do not build throwaway reference implementations or stubs to "prove" tests. RED for the right reason is the bar; review, CI and nightly mutation tests catch the rest.

## 5. Right model for the job (tokens)

| Role                                                       | Model / effort                                                                                  |
| ---------------------------------------------------------- | ----------------------------------------------------------------------------------------------- |
| Architect, reviewer, security reviewer, Tier A spec writer | Opus, high                                                                                      |
| Designer                                                   | Opus, medium                                                                                    |
| Test engineer, developers                                  | Sonnet: high for Tier A, medium for Tier B (the conductor passes the model and effort per call) |
| Researcher, planner                                        | Sonnet, medium                                                                                  |
| Release, triage, ops, bookkeeping                          | Haiku, low                                                                                      |

## 6. Pipelining and measurement

1. **Overlap:** while developers build feature N, the test engineer works on feature N+1 (separate worktrees). Independent features on different tracks run in parallel.
2. **Owner batching:** spec approvals and PR merges are batched once or twice a day.
3. **Metrics in `state.json`:** after every agent run the conductor appends `{"agent", "model", "tokens", "minutes", "slices"}` to `metrics` (from the task notification). Quality signals are appended at review time: `review_findings`, `ci_failures`, `post_merge_bugs`.
4. **Targets per standard feature:** ≤ 0.7M tokens, ≤ 1.5 h agent time, zero drop in quality signals. If quality signals worsen, the change that caused it is reverted.

## 7. The flow at a glance

```
Tier A: research → spec (owner ✓) → plan + brief → slices (skeleton first) → test pass → code pass → review + security → PR (owner ✓) → stage
Tier B:            spec + plan + brief (owner ✓) → slices (skeleton first) → test pass → code pass → review → PR (auto-merge when green) → stage
Release: stage → main PR (owner ✓) → production deploy (owner ✓)
```
