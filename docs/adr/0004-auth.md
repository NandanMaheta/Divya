# ADR 0004: Self-built auth in Go, Firebase only for SMS verification

- Status: Accepted (2026-11-13)

## Context

Clients sign up with email + mobile OTP, need owner approval, reset passwords and unlock with biometrics. Budget is ₹0; the owner wants backend depth on the resume.

## Decision

Go implements users, Argon2id password hashing, short-lived access tokens (JWT, 15 min) and rotating device-bound refresh tokens, lockout, and admin TOTP. Email OTPs go through Brevo/Resend. Mobile numbers are verified with Firebase phone auth on the client; the API verifies the Firebase ID token and marks the number verified. Biometric unlock protects the refresh token in the device secure store.

## Consequences

No auth vendor lock-in or MAU pricing; SMS stays within Firebase's free daily quota at this scale. We own security-critical code, so `internal/auth` PRs always need owner approval and security review.

## Amendment 1 (2026-11-13, feature 003 plan; proposed, accepted with the owner's approval of `specs/003-auth-core/plan.md`)

The decision above stands (self-built, JWT access tokens of 15 minutes, rotating device-bound refresh tokens). Feature 003 refines how it is applied:

1. **Revocation is checked on every request.** The access JWT (EdDSA, `kid` key ring) carries the device-session id; every authenticated request also loads that session and its user by primary key, so sign-out, device revocation, disabling and password changes take effect on the next request (spec D-05). The JWT still rejects forged or expired tokens before any database access.
2. **One refresh-token family per device session**, single use, stored only as SHA-256; any reuse or device-id mismatch ends the whole family at once, with no grace window (spec D-10, D-11).
3. **Refresh transport depends on the client.** Mobile apps receive the refresh token in the response body and keep it in the device secure store. The admin web panel receives it only in an `HttpOnly; Secure; SameSite=Strict` host-only cookie scoped to the refresh path, with Origin, custom-header and exact-CORS CSRF defences. This requires the admin panel and the API to share one registrable domain in staging and production (feature 027).
4. **Admin sign-in is password, then a short-lived single-use challenge, then TOTP** (or a single-use recovery code), with replay protection by last-accepted time step.
5. **JWT library**: `github.com/go-jose/go-jose/v4`, already present through the scheduler's OIDC verification, subject to the owner's dependency approval in the 003 plan.

Consequence: each authenticated request costs one indexed lookup (about 1–3 ms at this scale) in exchange for immediate revocation.
